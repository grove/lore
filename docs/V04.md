# Lore 0.4 — connect understanding

> In Lore 0.5, use `lore context --fast` for this deterministic retrieval contract. Default `lore context` provides schema 3 intelligent guidance; see [V05.md](V05.md).

Lore 0.4 connects documented intent with imported implementation reports, work history, and agent recollections. It keeps independent sources authoritative for their own records and stores its interpretation of their relationships separately.

An accepted ADR can document three retries while OpenWiki reports five at a particular evidence revision. Lore can surface a possible discrepancy with both sources, related history, and a verification question. It does not decide which code to write, infer a policy change from a closed issue, or claim that historical verification proves the current checkout's behavior.

## Configure local snapshots

Existing schema-version 1 configurations continue to work unchanged. Native imports require schema-version 2. Paths are resolved relative to `lore.yml`.

```yaml
schema_version: 2
project:
  name: payments
sources:
  roots:
    - id: decisions
      path: ./docs/decisions
      material: primary
imports:
  - id: implementation
    kind: openwiki
    path: ./openwiki
  - id: agent-memory
    kind: engram
    path: ./imports/engram.json
    project: payments
  - id: work-history
    kind: beads
    path: ./imports/beads.jsonl
    include_memories: false
```

Use the ordinary `models`, `providers`, and `privacy` settings. Cross-source inference uses the generative role and `models.reasoning.reconciliation` effort, including the configured local-only restriction. Import parsing and context retrieval do not invoke a model. New or changed documentary material and selected cross-source semantic comparisons can do so during `lore update`.

Imports are optional. Projects with only documents keep their existing configuration. An imports-only project sets `sources: { roots: [] }`; omitting `sources` keeps the normal `./docs` default. Import IDs and Markdown root IDs must be unique, and their paths must not overlap each other or generated output. Use a new import ID when switching an existing source to another adapter kind.

```bash
engram export ./imports/engram.json --project payments
bd export -o ./imports/beads.jsonl
lore update
lore --json context "Implement payment retries"
```

These upstream commands are preparation examples. Lore reads their existing local output and never executes them itself. OpenWiki must already have produced its OKF directory. Missing files, malformed records, unsupported declared versions, duplicate identities, or unsafe paths fail the update; missing input is not interpreted as bulk deletion.

## Supported native contracts

| Source | Accepted surface | Retained meaning |
| --- | --- | --- |
| OpenWiki | OKF `0.2` root `index.md`, concept Markdown, and `.claims/<page>.json` sidecars with `schemaVersion: 1` | Native claim IDs, statements, opaque resource versions, page provenance, durable verification metadata, and source links. Concept pages without sidecars remain derived documentation. |
| Engram | JSON export `version: "0.1.0"` or `"0.2.0"` | Observations, stable `sync_id` where present, legacy observation IDs, topic keys, source scope, project membership, deletion state, and native memory relationships. |
| Beads | Native issue JSONL, with legacy issue rows or `_type: "issue"` | Work lifecycle, original issue fields, exported descriptions/design/notes/comments, labels, references, dependencies, and history actually present in the export. `_type: "memory"` and legacy memory issues require explicit opt-in. |

Beads' issue export has no universal schema-version envelope; Lore does not invent one. Engram's `project` filter uses an observation's explicit project first and its session's project when needed. Relationships in a filtered Engram export remain within the selected endpoint set. Native IDs are scoped by the configured import, so unrelated databases cannot silently overwrite one another.

The adapter contracts follow [OpenWiki Claims types](https://github.com/langchain-ai/openwiki/blob/main/src/claims/brains/code/types.ts), [OpenWiki Claims storage](https://github.com/langchain-ai/openwiki/blob/main/src/claims/brains/code/store.ts), [Engram store/export](https://github.com/Gentleman-Programming/engram/blob/main/internal/store/store.go), [Engram relationships](https://github.com/Gentleman-Programming/engram/blob/main/internal/store/relations.go), and [Beads](https://github.com/gastownhall/beads). New upstream formats must receive an explicit adapter update; an unsupported OpenWiki directory can still be supplied through the ordinary derived-Markdown source path.

## Separate dimensions, preserved evidence

Each native observation retains source origin, knowledge kind, subject, scope, lifecycle, verification, source timestamp, native identity, and evidence references. These do not collapse into a confidence score. A Beads status can be reliable evidence that a workflow event occurred without proving what runs in production.

Normalized kinds are `implementation`, `recollection`, `work_state`, and `documentation`. Verification is independently `documentary`, `reported`, or `upstream_verified_at_revision`. Lifecycles remain source-native, so a work record's `closed` is not renamed to accepted architectural intent. Deleted or withdrawn observations retain history and are qualified accordingly.

Lore stores the original parsed native JSON, unrecognized fields where permitted by the source contract, source-owned metadata, and a content hash. The hash covers canonical parsed JSON rather than original whitespace or key order. A separate normalized hash protects the interpreted fields and attached upstream relations. Exact document quotations continue to use the existing Markdown validator; native evidence uses resolvable RFC 6901 record pointers and opaque source locators instead.

```bash
lore --json evidence ne_EXACT_ID_RETURNED_BY_CONTEXT
```

The result includes `evidence_type: "structured_native_record"`, the original record and metadata, the snapshot and native identity, its content hash, and whether the snapshot is current in the imported registry. Old evidence IDs continue to resolve after changes or withdrawal. SQLite migrations 6 and 7 add native observations and cross-source interpretation history; immutable tables and foreign-key checks protect retained evidence. `lore audit` validates both documentary and structured evidence.

### Freshness is explicit

OpenWiki's `pageVersion` and evidence `version` values have distinct meanings. Resource versions can be resolver-owned tokens such as `repo-lines-v1:…`; they must not be interpreted as Git SHA values. A durable upstream verification event applies only to its recorded evidence revision. When a sidecar lacks that event, the claim remains reported.

Lore verifies that a Claims sidecar's `pageVersion` matches the exact accompanying Markdown bytes. A mismatch fails the native import, preventing scope or metadata from an edited page from being attached to claims verified against another page version. This is stricter than OpenWiki's informational drift check: regenerate a coherent snapshot before importing it, or use the ordinary derived-Markdown root for a page without a matching Claims snapshot.

Lore 0.4 does not independently rerun OpenWiki's resolver, inspect live code, contact an upstream database, or verify production. `current: true` means that a snapshot was present in the last successful local import. It does not mean current code has been verified. Context retains this qualification and recommends checking the applicable implementation and policy.

## Incremental reconciliation

Native records are retained directly, without asking a model to write a new summary for each issue, memory, or claim. Candidate indexes use native identities, subjects, meaningful terms, references, and applicable source metadata to select bounded comparisons. Explicit upstream relationships are recorded with their native verb, direction, judgment status, and evidence; they do not become Lore-approved policy changes.

Known repository, component, or environment mismatches block a contradiction. Different applicable opaque revisions of the same source can represent historical change rather than disagreement. Unknown applicability remains qualified. Semantic judgments require exact supplied statement excerpts and affirmative compatibility before Lore records a possible discrepancy. Ambiguous comparisons remain unresolved and can create evidence-bound review items.

Recorded relation kinds include `potential_discrepancy`, `uncertain`, `verification_question`, `related_to`, `consistent_with`, and `upstream_relationship`. Source agreement is not independent verification. Shared upstream evidence is retained as shared provenance, without treating copied representations as independent confirmation.

Judgments, including negative comparisons, are keyed to their exact input revisions. Changed evidence reevaluates affected candidates and moves current pointers; old interpretations remain in history. The existing documentary engine continues to preserve explicit accepted replacements and their predecessor evidence. A work closure or memory relationship cannot silently supersede a documentary decision.

An automatic review question follows its specific comparison. When changed inputs no longer raise that question, Lore closes the obsolete item while retaining its evidence and event history. This is not independent implementation verification. Human dispositions remain in effect for unchanged inputs; changed evidence reopens a review only when the new interpretation raises a question.

Identical inputs produce a no-op update with zero model calls and no knowledge or output churn. Missing configured snapshots fail safely. Removing a record from an otherwise successfully read export withdraws current support while keeping historical evidence. Bounded comparison omissions are persisted as warnings; they are not evidence that all sources were compared.

Semantic judgments also depend on the configured model and reasoning policy. Configuration changes invalidate those judgments, and explicit `--refresh` / `audit --deep` creates a new reconciliation epoch rather than silently reusing prior semantic decisions. Deterministic upstream relationships continue to reuse their unchanged evidence.

## Context response, version 2

The command remains `lore context TASK`, with existing `--path`, `--max-tokens`, and global `--json` options. Retrieval is deterministic and uses only the last compiled local registry. It does not require provider credentials or perform inference, network requests, or database writes. Version 4 and 5 documentary registries remain readable without an automatic migration.

The JSON contract has `schema_version: 2`. Existing documentary fields remain, with these additions:

| Field | Meaning |
| --- | --- |
| `imported_observations` | Selected normalized source records, original authority, lifecycle, verification, freshness, qualifications, and evidence IDs. |
| `imported_evidence` | Resolvable native snapshot IDs, content hashes, source locators, captured/observed times, and metadata. Full native payloads remain available with `lore evidence`. |
| `cross_source_relations` | Stored relationships with complete selected endpoints, revisions, provenance, and upstream status where applicable. |
| `discrepancies` | Structured potential discrepancies and unresolved relationships, evidence bindings, qualifications, and review IDs. |
| `recommended_verification` | Evidence-linked checks to perform before relying on a reported result or changing behavior. |
| `omissions.imported_observations` / `omissions.discrepancies` | Relevant native records or discrepancy groups that did not fit the output budget. |
| `omissions.source_warnings` | Complete source diagnostics omitted or shortened in a bounded diagnostic summary, so a large archive cannot crowd all task evidence out of context. |

Consumers should check the schema version and support the new fields. The existing `sections`, `evidence`, `relations`, `reviews`, `budget`, `warnings`, and retrieval-truncation fields retain their documentary roles. Markdown evidence is not relabeled as native JSON evidence.

Retrieval includes native IDs, issue references, source components, source-cited paths, and stored cross-source relationships. Related documentary and native endpoints form an atomic selection group: when a group cannot fit, Lore omits the group and reports the omission instead of presenting one side as complete guidance. Both the entire compact JSON response and the human-readable output fit the requested token budget. Long source records or wide connected groups can require a larger budget.

Human output adds observed implementation, related history, potential discrepancies, and recommended verification beside the existing documentary sections. The generated wiki's `imports.md` page supplies a compact entry point with source counts and retained cross-source questions. It does not generate thousands of redundant summaries.

## Validation and release boundary

Run the full offline contracts with:

```bash
cargo fmt --all -- --check
cargo test --all-targets --locked
python -m unittest discover -s evaluation/tests -v
```

Tests cover supported source contracts, optional imports, source filtering, immutable evidence, migration, idempotence, changes and withdrawal, scope/revision incompatibility, closed work and stale memories, shared provenance, review history, deterministic retrieval, complete grouping, budget omissions, and citation resolution. The end-to-end ADR/OpenWiki slice verifies that a mismatch reaches task context and that changed evidence retains historical snapshots.

[Cross-source evaluation](../evaluation/CROSS_SOURCE.md) adds multiple project scenarios and a four-setup comparison: code/docs, OpenWiki, OpenWiki plus Engram plus Beads, and the same tools plus Lore. It tracks preparation and retrieval cost, mechanically resolvable imported citations, unchanged-import churn, and blind reviewer annotations. The proposed gates are a 20% reduction in missed critical constraints against the strongest relevant baseline, no increase in unsupported authoritative claims, zero high-severity unsupported claims, and at most 10% false discrepancy warnings.

These quality thresholds require real model-enabled runs and independent held-out human review. Passing fixtures establishes mechanical behavior, not a measured incremental benefit or a passed semantic release gate. No benchmark result is implied by the version number.

Live synchronization, daemons, bidirectional writes, autonomous code analysis, a new graphical interface, a graph database, and an orchestration engine remain outside 0.4. Arbitrary synonym recall, all-pairs reconciliation, and current-code verification are not claimed.
