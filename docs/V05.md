# Lore 0.5: actionable project intelligence

Lore 0.5 turns retained project knowledge into a task briefing: one preferred
approach, relevant history, plausible interpretations, important risks, and
useful next steps. The underlying registry remains the record of source-backed
knowledge. Generated advice is revision-bound, inspectable, and disposable.

## The everyday workflow

```bash
lore context "Implement payment retries"
lore --json context "Replace the payment processor"
lore context "Change release validation" --path src/releases

# Deterministic retrieval with the existing 0.4 JSON contract:
lore --json context "Implement payment retries" --fast

# Regenerate guidance without reading or writing disposable context caches:
lore context "Implement payment retries" --no-cache
```

Default context uses the configured generative model. A suitable local provider
can produce intelligence without hosted access. If generation is unavailable,
blocked by local-only policy, or fails output validation, Lore returns an
explicit fast fallback so ordinary retrieval remains usable.

For example, a useful payment briefing can recommend preserving the currently
reported retry behavior while explaining that an accepted ADR says something
different. It can connect incident recollections and work history to a likely
rationale, offer an alternative explanation, and suggest inspecting idempotency
tests and the relevant incident record. It cannot silently declare the ADR
replaced, treat a closed issue as deployment proof, or claim that an imported
OpenWiki observation verifies today's checkout.

This is an illustrative product behavior, not a statement about any live
payment project. Actual output depends on the retained evidence and model.

## Three explicit response contracts

| Invocation/result | JSON | Interpretation |
| --- | --- | --- |
| `context --fast` | Schema 2, the existing context response | Deterministic retrieval; zero inference and no cache changes |
| Successful default context | Schema 3, `mode: intelligent` | A generated and validated task briefing with exact evidence manifests |
| Unavailable or rejected reasoning | Schema 3, `mode: fast_fallback`, `fallback_reason` | The deterministic context fields remain at the top level, with explicit fallback metadata |

Agents should select behavior from `schema_version` and `mode`. A fallback
does not contain fresh generated reasoning. Successful intelligence includes
`model_calls`, `model`, `cache_status`, the output `budget`, and `brief`:

| Brief field | Purpose |
| --- | --- |
| `preferred_approach` | The concise implementation direction to act on first |
| `known` | Exact selected registry statements with their original lifecycle, basis, qualifications, and citations |
| `inferred` | Derived hypotheses with confidence, applicability, alternative explanations, and evidence revisions |
| `recommended` | Further evidence-linked guidance |
| `risks` | Consequences to consider, including security, financial correctness, destructive changes, and accepted constraints |
| `next_steps` | Targeted inspections or checks that move the task forward |
| `constraint_checks` | Explicit treatment of selected adopted decisions and constraints |
| `scrutiny` | The risk categories and support-check status applied to the briefing |

Every generated advice item and interpretation must use exact selected
evidence IDs. `known` statements come from registry records, rather than a
model-generated restatement. Compact `evidence` manifests retain source,
revision, content hash, basis, and current/historical status; resolve the actual
quotation or native snapshot with `lore evidence ID`. Suggested code locations
come from retained inspection references and do not assert that Lore inspected
a current working tree.

The token budget applies to complete JSON and text output. Lore removes whole
items to fit and reports omissions. A small budget can require fallback; it
does not authorize broken citations or a silently truncated JSON response.

## Optional hybrid retrieval

Configure `models.embedding` to combine embedding similarity with existing
SQLite FTS5 lexical retrieval. Lore embeds original knowledge records and
imported observations, fuses lexical and semantic ranks, then uses recorded
relationships to expand selected groups. Generated wiki pages are not the only
retrieval surface.

The implementation uses SQLite as a disposable vector cache and calculates
cosine similarity in process. No Node.js runtime, QMD service, vector extension,
or graph database is mandatory. Vectors are reused incrementally when their
record revision and embedding model identity still match. Query vectors are
cached too. If embeddings are absent or unavailable, lexical retrieval and
relationship expansion remain available with explicit diagnostics.

This deliberately bounded implementation favors a simple local installation.
Semantic similarity is a retrieval signal, not confidence in an assertion.
Large corpora, shortened record text, candidate limits, and source vocabulary
can still lead to omissions. Benchmark independent projects before claiming a
retrieval advantage or choosing a larger search backend.

## Model configuration, privacy, and caching

The existing generative model and provider settings are reused. The new
reasoning tasks are `context_synthesis` (default `medium`) and
`context_verification` (default `high`). They follow the same configurable
reasoning policy as extraction and wiki synthesis. See
[REASONING.md](REASONING.md) and the complete local configuration in
[lore.intelligent.yml](../examples/lore.intelligent.yml).

Semantic retrieval has its own optional embedding role. Hosted inference still
requires explicit provider configuration and disabling local-only policy.
Lore does not silently route failed local inference to a hosted provider.

The registry and original source files remain unchanged by either context
mode. Intelligent context stores disposable guidance under the state
directory's `context-cache` and optional vectors in `semantic.sqlite3`, separate
from `state.db`. `context.cache: false` or `--no-cache` disables reuse and writes
for these context caches. `--fast` bypasses intelligence and embedding work
entirely.

Guidance reuse is bound to the task, selected evidence revisions, model
identity, prompt/schema rules, and reasoning configuration. A changed source
revision, source selection, or relevant configuration makes prior guidance
inapplicable. Cached derived insights do not change an accepted decision's
lifecycle. Repeated identical queries can reuse valid guidance without
additional inference; cache and call metadata make this visible.

## Reasoning boundaries

Hypotheses are allowed to be useful before they are certain. Lore can propose
that a policy document is outdated, explain why the evidence supports that
interpretation, and recommend a provisional approach. Each hypothesis retains
its evidence, applicability, an alternative explanation, and revision identity.
Historical-only support stays labeled historical. Corroboration and freshness
are interpreted within their recorded scope; capture time alone is not event
ordering.

The validation layer rejects unknown or mismatched evidence references.
Adopted constraints must be explicitly addressed. A proposed deviation needs
an acknowledged risk and a useful verification step. Consequential guidance
and causal hypotheses receive an additional model support check before use.
That support check is another interpretation of retained evidence, not
independent proof of correctness. A failed check produces an explicit fallback.

The release does not introduce autonomous code changes, policy edits,
background agents, new live issue-tracker synchronization, or a general agent
framework. Coding agents continue to decide and execute their own changes.

## Practical evaluation

[The 0.5 evaluation guide](../evaluation/INTELLIGENCE.md) describes executable
coding-task comparisons for baseline sources, fast context, and intelligent
context. It extends the existing tooling and cross-source fixtures with actual
proposed implementations and external correctness/constraint checks.

The collector records source preservation, exact citation resolution, fast
determinism, repeated context behavior, first/repeat latency, model calls,
provider-reported coding tokens, and measured billing when available. It
creates anonymous unscored human-review packets for usefulness, implementation
quality, missed constraints, and unsupported authority. Unknown costs stay
unknown; fallback responses are not counted as intelligent outcomes.

Offline tests verify these mechanics and fixture behavior. They do not
establish a measured quality improvement over `--fast`, independent coding-agent
benefit, or lower cost. The release's evaluation materials make those remaining
measurements explicit. A useful next validation is a small blind comparison on
held-out projects, holding the coding model, source revision, settings, and task
budget fixed while varying context mode.
