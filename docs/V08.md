# Lore 0.8 — useful first contact and measurable work

Lore 0.8 provides immediate assistance from local project documents, makes
adaptive task intelligence the initialized-project default, and records
provider attempts without inventing token usage or bills. It also adds a
controlled Guardian integrity replay and a launch/retention wrapper for genuine
coding studies. The existing evidence registry, decision engine and permission
boundaries remain the foundation.

The [0.8 scorecard](../evaluation/PRODUCT_QUALITY_08.md) records final source
revisions, merge receipts, platform gates and artifact hashes. Real-model coding
productivity, human first-contribution time and learning transfer, and
independently reviewed Guardian alert quality remain **unmeasured**. A package
version, passing fixture, cache hit or prepared study does not establish those
outcomes. [The 0.7 guide](V07.md) and its scorecard remain historical records.

## Start from the project directory

After installing Lore, ordinary first-contact commands work before configuring
a model or compiling a registry:

~~~bash
cd /path/to/your-project
lore context "Change retry handling"
lore --json context "What is QUEUE_CAPACITY?"
lore onboard
lore onboard --task "Improve dispatch diagnostics"
~~~

When eligible documents exist, the result points to a useful local starting
place and includes exact source passages. If evidence is missing or incomplete,
the response says so. This path constructs no provider, creates no configuration
or registry, writes no cache or source, and makes no network request. An
explicitly requested usage-ledger file is separate caller-owned output, as
described below.

### A distinct bootstrap contract

JSON identifies the first-contact result with:

| Field | Meaning |
| --- | --- |
| contract | lore.bootstrap_context or lore.bootstrap_onboard |
| schema_version | 1 for this separately named contract |
| mode | bootstrap_source_only |
| source_snapshot_sha256 | Digest of the selected local documentary identities; not a retained-registry revision |
| evidence | Exact relative paths, full-file SHA-256 values, line spans and source excerpts |
| best_next_action | Documentary navigation or an explicit evidence-limited next step |
| limitations and omitted_source_groups | Unestablished claims and complete groups omitted from the selection |
| model_calls and source_write | Zero model calls and no primary-source modification |
| budget | Measurement of the complete JSON and Markdown response |

Discovery considers root Markdown and recognized documentation, ADR, decision,
design, RFC, architecture and specification directories. A valid existing
configuration constrains discovery to its eligible Markdown roots inside the
project. Native imports and configured external roots require explicit
compilation. Missing explicitly selected configurations, malformed configuration,
denied paths and pending publication are errors; they do not silently select
another root. An existing registry whose configuration disappeared also requires
restoring or explicitly selecting that configuration.

The source reader enforces **256 files, 8 MiB total, 1 MiB per file and eight
directory levels**. Configuration and local ignore bytes count toward the read
envelope. Directory enumeration is additionally bounded to 16,384 entries and
two seconds per directory. It honors local .gitignore and configured exclusions
and skips symlinks, hidden/vendor/build/cache directories and generated output.
Granting inspection does not turn bootstrap into a source-code scanner.

Selection keeps complete documentary bundles: the relevant section, required
preamble, descendants, scope, sibling exceptions and linked local sections.
Ambiguous grouping retains the document. A bundle that cannot fit is omitted
with a count; included quotations are not shortened to manufacture completeness.
Other qualifications can remain outside the selected groups. Documentation is
evidence of what a source says, not proof of runtime behavior or an independent
policy assessment.

The [bootstrap implementation](../src/bootstrap.rs) and
[first-contact regression tests](../tests/bootstrap_cli.rs) define the exact
discovery, revalidation and complete-output limits.

## Choose durable initialization when needed

Configuration and compilation remain explicit actions:

~~~bash
lore init --configure-only --source ./docs --source ./plans
# Edit lore.yml to select the actual sources and available models.
lore init
lore status
~~~

Configure-only writes a configuration without running inference. Compilation
can call the selected provider and writes Lore-owned state and generated pages.
Use the project's approved model and egress policy. A first-contact response
does not initialize a project or manufacture retained knowledge.

Before compilation, explicit context schemas 3, 4 and 5 and the deterministic
--fast contract return the typed uninitialized_project error. Tutorial, hint,
answer and transfer activities likewise require compiled intelligence. Plain
onboarding and direct task navigation remain available from local documents.

## Adaptive context is the initialized default

~~~bash
lore context "Refactor retries without changing behavior"
lore --json context "Refactor retries without changing behavior"
lore --json context "Refactor retries" --schema-version 5
~~~

These initialized-project requests use the existing adaptive controller and
schema-5 envelope. Markdown leads with the preferred approach, next action,
complete critical constraints and material decisions before supporting
rationale and detail. Facts, documentary intent, source-reported outcomes,
static observations, hypotheses and general engineering judgment retain their
different evidential status. Proposed completion checks describe future work.

For JSON consumers, read snapshot, capabilities, intelligence,
source_relationships, budget and usage together. The nested intelligence.mode
distinguishes an intelligent brief, an exact retained reference and an honest
fast_fallback. A fallback has a reason and no fresh model assessment. Selected
relationship groups preserve original endpoints, source-owned reasons and
review/history qualifications even when optional brief prose is removed.

An exact supported symbolic question, such as "What is QUEUE_CAPACITY?", can
return reference mode with zero model calls, checkout reads or cache work.
Changing that constant or resolving material contradictory evidence still uses
the ordinary decision path. A denied capability leaves the strongest permitted
evidence available; it is not an invented policy prohibition.

### Schema migration for consuming agents

| Invocation | Initialized-project contract | Before compilation |
| --- | --- | --- |
| lore context TASK | Adaptive schema 5 | Separate bootstrap source-only contract |
| lore context TASK --schema-version 5 | Adaptive schema 5, explicitly pinned | uninitialized_project |
| lore context TASK --schema-version 4 | Existing schema-4 decision/fallback and Markdown ordering | uninitialized_project |
| lore context TASK --schema-version 3 | Existing schema-3 intelligence contract | uninitialized_project |
| lore context TASK --fast | Existing deterministic schema 2; zero model calls | uninitialized_project |

Use [the copyable agent instructions](AGENTS.example.md) to pin schema 5,
preserve evidence qualifications and perform the coding agent's own authorized
implementation checks. Agent instructions are optional. Lore installs no
mandatory integration and gives quoted project instructions no new authority.

The default output budget remains 3,000 offline cl100k_base tokens. Both the
complete emitted JSON and Markdown must fit, including snapshots, capabilities,
source relationships, citations, usage and omission metadata. Required
conditions stay together. If the smallest complete package cannot fit, the
command returns an actionable budget error. Provider tokens are a separate
measurement.

## Model and permission matrix

The following rules describe the default adaptive experience. Explicit schemas
3/4 retain their established compatibility behavior.

| Situation | Permitted work and result |
| --- | --- |
| Bootstrap before compilation | Eligible local document reads; zero provider requests or code inspection |
| Deterministic --fast or an exact retained reference | Retained documentary/native evidence; zero new model requests |
| Initialized request with a configured local, non-cloud Ollama model | Local inference within configured limits; no hosted fallback |
| No caller inspection grant | Retained project evidence; repository settings alone cannot enable checkout reads |
| LORE_INSPECTION_ROOT supplied by the invoking host | Bounded automatic inspection within that root; configuration may narrow it |
| --inspect or --investigate | Grants the configuration directory for the invocation, within any standing ceiling |
| --no-inspect with a standing grant | Inspection is denied; incompatible explicit flags are rejected before work |
| Hosted model with local_only enabled or no caller hosted grant | Hosted inference is denied and permitted fallback remains available |
| Hosted documentary inference | Requires privacy.local_only: false and LORE_ALLOW_HOSTED_EGRESS=1 |
| Hosted checkout content or discovered filenames | Also requires the separate checkout grant and configuration, or the explicit per-invocation --allow-checkout-egress grant |
| Timeout, refusal, malformed output or unavailable provider | Attempts retain their observed accounting; fallback or an explicit error keeps limitations visible |

For a standing local read grant:

~~~bash
LORE_INSPECTION_ROOT="$PWD" lore context "Refactor retries"
LORE_INSPECTION_ROOT="$PWD" lore context "Refactor retries" --no-inspect
~~~

For hosted checkout use through standing grants, the caller supplies
LORE_ALLOW_HOSTED_EGRESS=1 and LORE_ALLOW_CHECKOUT_EGRESS=1, while the configuration
sets privacy.local_only: false and privacy.allow_checkout_egress: true.
The explicit --allow-checkout-egress option supplies both per-invocation hosted
and checkout permission within the local-only ceiling. It does not grant
execution or widen the inspection root. Environment credentials by themselves
are not a grant.

The [shared-intelligence guide](SHARED_INTELLIGENCE.md#standing-grants) documents
the exact composition. Reused findings remain bound to the retained registry,
actual grants and every observed file hash. Newly retained counterevidence,
deep-file changes and reduced grants invalidate or narrow reuse. A snapshot is
an identity for retained evidence, not a promise that all live sources were
refreshed; updating documentary state is an explicit lore update operation.

## Provider usage and SQLite schema 8

Schema 5 now carries additive usage accounting. Generation, decision and
embedding attempts retain logical call IDs, HTTP attempts, retries, cache
events, elapsed time and outcome status. A transport attempt can fail before
reaching the provider; request counts do not prove billable execution.

Input, output and total tokens are nullable nonnegative integers. Totals are
derived only when valid component counts permit it. Unsupported, absent,
malformed or inconsistent accounting stays unknown. Billed USD stays null
unless an actual measured amount and billing source exist; local model use is
not treated as a free invoice. No guessed price table is included.

A verified cache hit has zero new provider requests and tokens. Historical
generation cost remains separate. Unknown components propagate through totals.
Neither an offline response-envelope token count nor a logical model-call count
is substituted for provider token usage.

Accounting stays in memory by default. A host can explicitly select a new,
absolute ledger path in an existing directory:

~~~bash
LORE_USAGE_LEDGER=/absolute/private/audit/attempt-001.json \
  lore --json context "Implement payment retries" --schema-version 5
~~~

The selected path must not exist or traverse a symlink. This is caller-owned
output, including with --no-cache. The versioned lore.provider_usage ledger
retains started, failed, refused, timed-out, cancelled and completed attempts
without raw prompts, source text, provider bodies, endpoint URLs or credentials.
Abrupt termination can leave a started event; it is not a completed zero-cost
request. Evaluators read their own selected ledger and verify its exact bytes
and event sum rather than following an untrusted response path.

Successful compilation stores usage through the additive SQLite schema-8
migration. Historical schema-7 model-call records remain intact and unknown
usage is not backfilled. Failed work stays in the invocation sink rather than
an incomplete published generation. Older binaries cannot write schema 8;
downgrading requires a consistent pre-upgrade project backup. No destructive
reverse migration is provided.

See [PROVIDER_USAGE.md](PROVIDER_USAGE.md) for supported provider mappings,
cross-language hash bindings, custom adapter compatibility and evaluator costs.

## Guardian integrity and advisory boundaries

~~~bash
lore baseline save before-change
# After an authorized source change and explicit compilation:
lore update
lore changes --since before-change
lore guard --since before-change --no-inspect
~~~

Guardian remains an on-demand advisory over retained source states. It does not
monitor in the background, execute project commands or modify primary sources.
An uncompiled live edit is outside the named-baseline comparison. Missing
alerts do not prove the absence of risk.

The 0.7 archived failures remain failures. During the 0.8 investigation,
restoration reproduced in a control that started zero Lore or other subprocesses,
positively isolating external activity in that workspace. Temporary-file writes
and renames were observed; the writer executable/PID and the historical writer
were not authenticated. A later clean replay does not retroactively identify
that writer.

The supported integrity workflow uses fresh Ubuntu runner storage, frozen
baseline and candidate binaries, one exact source/history preparation and
independent Linux inotify observation. It runs both complete 60-event cohorts,
a repeated full candidate, the focused 10-event segment and a 60-event no-Lore
control. Every event and command must preserve the original byte oracle, with
complete source observation and zero provider calls. Missing observations or
unclassified writes fail the gate. Final results and capture hashes belong in
the [0.8 scorecard](../evaluation/PRODUCT_QUALITY_08.md).

Per-command inventories retain file identities, hashes and metadata. Path and
descriptor timestamps are compared within their respective APIs to accommodate
the documented Windows ctime distinction without dropping change detection.
Inotify does not supply writer PIDs or an execution/egress audit. Source
integrity is separate from independently reviewed precision, recall, alert
burden and usefulness. See [the longitudinal protocol](../evaluation/GUARDIAN_LONGITUDINAL.md)
and [the dedicated workflow](../.github/workflows/guardian-integrity.yml).

## Genuine coding and human studies

The [study wrapper](../evaluation/EXPERIMENT_08.md) uses the six existing arms:
baseline, fast, lore05, lore06, adaptive_no_reuse and adaptive_reuse. Preflight
checks pinned sources/checkers, independent gold review, configured models and
revisions, exact commands/prompts, grants, tools, budgets, output privacy and
fresh external availability/isolation/egress evidence. Sealing does not invent
human identity authentication or create an operating-system sandbox.

Preparation, pins, seal, preflight and assessment make no provider calls.
Launch requires every gate, freezes the validated arguments and rechecks the
sealed inputs immediately before creating the existing runner. Timeout,
cancellation and persistence failure stop and reap the process group. The
supported launch environment is private POSIX storage with externally enforced
isolation; Windows preparation and inspection remain available.

Every planned assignment and actual invocation remains visible, including
refusals, failures and incomplete work. A six-task, three-project pilot has
36 planned initial assignments; a separate reviewed holdout has at least
30 tasks and 180 assignments. Public candidate tasks cannot be relabeled as
held-out evidence. Full costs include initialization, warm-up, revalidation,
coding, repair, checking and observed waits. Unknown totals stay null.

The checked-in [readiness receipt](../evaluation/results/experiment-08-readiness/README.md)
records **not_run**: six public candidate tasks, 36 planned assignments,
**zero actual coding attempts and provider calls**. Configured model identities,
independent review and authenticated external readiness were missing.
The matched different-task sequence adds a new accepted contradictory ADR,
deep-file mutation and reduced grants; it reports measured total-cost
differences when actually run. A cache hit alone is not time saved or a
memory-only causal ablation. No speculative retrieval/controller change is
justified by the unrun pilot.

The [human protocol](../evaluation/HUMAN_ONBOARDING.md) prepares twelve
counterbalanced positions and **zero real participants**. Actual consent,
pseudonymous sessions, source-bound contributions, assistance/time records,
independent checks and a distinct task with reduced assistance are required
before first-contribution or transfer outcomes can be measured. An agent's
patch is not human competence. Ordinary onboard navigation remains available
without enrolling in a study or starting an optional tutorial.

## Reproduce the engineering gates

Use a current stable Rust toolchain and Python, with fresh output directories.
Regular CI uses local fixtures and provider doubles without paid inference:

~~~bash
cargo fmt --all -- --check
cargo clippy --all-targets --locked -- -D warnings
cargo test --all-targets --locked
python3 -m unittest discover -s evaluation/tests -v
cargo build --release --locked

target/release/lore --version
target/release/lore --help
target/release/lore context --help
target/release/lore onboard --help
target/release/lore baseline --help
target/release/lore guard --help
~~~

On Windows use the installed Python command and target/release/lore.exe.
The standard matrix covers Linux, macOS and Windows, including release-mode
build and CLI smoke checks. Its tests also cover migration, no-op updates,
recoverable publication, cancellation, purge boundaries, provider failure,
source permissions and complete response budgets. The controlled Guardian
workflow is a separate integrity gate.

Prepare the new study inputs and retained-source sequence without a model:

~~~bash
python3 evaluation/real_coding_corpus.py prepare --pilot \
  --output /ABSOLUTE/PATH/lore-08-pilot-inputs
python3 evaluation/experiment_08.py prepare \
  --cases /ABSOLUTE/PATH/lore-08-pilot-inputs/cases.json \
  --output /ABSOLUTE/PATH/lore-08-pilot-study
python3 evaluation/experiment_08.py preflight /ABSOLUTE/PATH/lore-08-pilot-study
python3 evaluation/adaptive_sequences.py prepare \
  --cases evaluation/corpora/adaptive-sequences-08/cases.json \
  --output /ABSOLUTE/PATH/lore-08-sequences
python3 evaluation/human_onboarding.py prepare \
  --output /ABSOLUTE/PATH/lore-08-humans
python3 evaluation/guardian_longitudinal.py prepare \
  --output /ABSOLUTE/PATH/lore-08-guardian
~~~

The incomplete study preflight is expected to exit 2 and record its actual
blockers. Checker validation executes controlled candidate code and belongs
in the documented study/test environment. A provider, reviewer or participant
is never substituted merely to obtain a passing report.
