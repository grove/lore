# Lore 0.2 — knowledge quality and review usability

Lore 0.2 implements the next quality-focused milestone: documented design is a first-class knowledge kind; review questions have an evidence-bound lifecycle and human CLI dispositions; the project overview is synthesized with citations; and the evaluator can run Atlas, Lore and OpenWiki as a repeatable suite. This is an implementation milestone, **not a declaration that all providers or all projects have achieved validated-beta quality**. The previous user-run Atlas benchmark at `9479727` passed its three relationship checks, but those results do not measure the new classification or overview prompts.

## Upgrade an existing project

Pull the repository and install the new binary with `cargo install --path . --locked`. The package version is 0.2.0. SQLite migration 4 adds review contexts and append-only review events without rewriting the earlier evidence snapshots or knowledge revisions. The first `lore update` after this upgrade changes the pipeline fingerprint, so it intentionally re-examines the sources and can make model calls. Back up your local state before upgrading and budget for that first refresh. Subsequent genuinely unchanged updates retain zero-model-call behavior. Normal edits to generated pages still require explicit handling; the upgrade does not authorize overwriting human work.

## Design is not the same thing as a plan

`design` represents the selected architecture or specification documented by a project. A sentence describing the ledger's documented data flow does not become future work merely because Lore has not verified the running service. Explicit possible changes remain `proposal` or `plan`, and a source claiming delivery remains `reported_outcome`. Mandatory rules use `constraint`, while an ordered operating process can use `procedure`. Type and lifecycle are separate from evidential certainty; none of these types establishes independent implementation verification. Extraction guidance and strict JSON contracts now express these distinctions, and topic prose displays them consistently. Actual classification accuracy remains a model-evaluation question, not something a fixture test proves.

## Inspect and resolve reviews

Run `lore review` or `lore review list` for pending questions, `lore review list --all` for retained records, and `lore review show REVIEW_ID` for the original reason, exact source/target binding and transition history. A reviewer can use `lore review resolve REVIEW_ID --reason "Inspected the linked decisions" --actor "reviewer-name"`, or choose `dismiss` and `reopen` with the same required reason. Actor labels are supplied by the user; they are audit attribution, not authentication. Commands perform no model inference and do not edit the knowledge graph, change source evidence, or declare an implementation true. They atomically republish the review-history page and the overview's queue count through the existing recoverable publication mechanism, leaving topic prose intact.

Automatic resolution is narrower than human disposition. A question about an accepted decision's replacement or reaffirmation can close when an active explicit relation from the **same source revision** to the **same predecessor** provides a unique documentary answer. An unrelated topic, a different source, a proposal, or a generic ambiguity is insufficient. The resolution event cites the actual relationship evidence snapshot. If that evidence disappears, the question reopens with another recorded event. A human disposition remains in effect until its bound source/knowledge context changes, at which point it is reopened for review rather than silently treated as permanent approval. Legacy records are linked only when their original hashed machine key can be reconstructed exactly; unknown legacy questions stay reviewable.

## A useful project entrance

The index now contains a generative project narrative, with known-ID citations and a second semantic support check when `verify_synthesis` is enabled (the default). It explains major documented systems, decisions, initiatives and unresolved questions rather than only listing pages. Its context includes representative knowledge from every topic and explicit decision relationships; all material assertions remain on their topic pages. Context limits are explicit: a project with too many large topics to represent safely causes an actionable budget error rather than silently omitting topics. Overview generation adds model work on changed projects; review-only dispositions and unchanged runs do not regenerate the narrative.

Decision navigation uses source-document labels, such as **ADR-027 explicitly supersedes ADR-001**, even when both decisions reside on the same topic page. Citations use the evidence attached to that exact relationship, not an arbitrary supporting quote. Explicit connected decision chains are available to affected topic writers and verifiers, so a reaffirmation page also sees a later replacement of the decision it reaffirms. Stable topic identities and unrelated-page byte preservation remain regression-tested constraints.

## Cross-project validation

The [evaluation guide](../evaluation/README.md) covers `evaluation/suite.py`. `prepare` copies the allowed Atlas, Lore and pinned OpenWiki Markdown into separate workspaces without inference. `run` invokes the real CLI, performs Atlas's mutation, checks no-op behavior, retains each independent run, and can repeat runs with fresh caches. Separate `--generative-base-url` and `--decision-base-url` flags allow the existing Foundry generative endpoint and local Ollama decisions to be selected explicitly. Hosted access still requires `--allow-hosted`; no provider credentials are written into the report.

Each successful suite run creates an unscored `HUMAN_REVIEW.json` bound to the exact metrics, wiki pages, source corpus and binary fingerprint. A reviewer must fill seven scores, notes and valid evidence IDs before `suite.py assess` can pass the human gate. All seven scores must be at least 2/3, no critical error may remain, and the automated checks must pass on Atlas, Lore and OpenWiki for the candidate gate. These are small-corpus reviewer-attested acceptance rules, not universal factual-accuracy claims. Missing human scores never turn into zeros or fabricated passes.

The Atlas rubric now recognizes documented design and explicitly permits `procedure / active` for a mandatory operational gate. The old rubric remains in `evaluation/gold/archive/atlas-v1.json`. Reports record rubric hashes, and comparisons flag rubric or configuration changes; a higher score obtained by changing labels is not evidence of a better model. Candidate matching optimization, token/billing instrumentation, aggressive deduplication, direct issue-tracker connectors, and independent runtime verification remain outside this milestone.
