# Lore 0.7 — evidence-driven usefulness

Lore 0.7 improves constrained-budget evidence retrieval and the reliability of
project change comparisons. It also provides reproducible protocols for actual
coding attempts, human first contributions and learning transfer, and
longitudinal guardian evaluation. The [release scorecard](../evaluation/PRODUCT_QUALITY_07.md)
distinguishes measured engineering and retrieval results from product outcomes
that still require real models, independent reviewers and consenting people.

## Retrieve complete conditions within a small budget

Use the explicit compact response when the original exploration envelope takes
too much room:

```sh
lore explore "increase queue capacity" --compact --max-tokens 1500
lore --json explore "increase queue capacity" --compact --max-tokens 1500
lore explore --node RETURNED_VIEW_ID --compact --max-tokens 3000
lore evidence RETURNED_EVIDENCE_ID
```

Selection treats a directly applicable rule, its exception, its historical or
scope qualification, and the endpoints and witness of a documentary relation as
one evidence obligation. A shared topic or an ordinary word is a relevance
signal; it does not make every rule in that topic inseparable. Complete factual
support receives budget before optional navigation.

The response includes the actual original statement, type, lifecycle, scope,
source revision and source quotation. Lore does not shorten the exception or
discard a historical endpoint to make a result fit. When a complete obligation
cannot fit, `partial` or `budget_limited` and the omission fields identify the
limitation. A successful retrieval does not establish that a documented claim
was verified in a running application.

`--compact` selects **exploration schema 2**. The JSON stores repeated strings
and evidence in normalized tables, and the Rust `CompactExploreResult::resolve`
method reconstructs the full records without accessing a database or a model.
The resolved object is for reading; its larger serialization is not the compact
wire response whose tokens were counted. Both the complete emitted JSON and
portable Markdown must fit the requested budget, including metadata and
omission reporting. See [the exact row formats and resolver contract](KNOWLEDGE_ZOOM.md).

Plain `lore explore` keeps schema 1 and all its public fields. Schema 1 retains
its explicit budget limitations when its full envelope cannot hold a complete
answer. Existing `context` schemas 2, 3 and 4, deterministic `--fast`, and the
explicit schema-5 shared-intelligence path retain their selection mechanisms.

## Understand changes since an explicit checkpoint

```sh
lore update
lore baseline save before-change
# After the project's sources change:
lore update
lore changes --since before-change
lore guard --since before-change --no-inspect
```

The guardian remains an on-demand advisory command. It compares retained source
states against the named checkpoint; an uncompiled live edit is outside that
comparison. It uses the same evidence, standing permissions and bounded
investigation engine as task context.

0.7 records which evidence currently supports a revision separately from its
retained history. An A-to-B-to-A source-condition change therefore remains
visible even when the historical set of quotations already contains A and B.
Older saved baselines still validate under their original checksum contract.
Advisory topic selection prioritizes material accepted constraints and scope
changes, and duplicate risk/blocker descriptions share an actionable next step.
Original evidence and complete qualifications remain available.

An unavailable model, incomplete budget or partial static response stays labeled
as such. No alert is not proof that the project is safe. The
[guardian guide](PROJECT_COMPANION.md) documents the exact response and
permission contracts, and the [longitudinal protocol](../evaluation/GUARDIAN_LONGITUDINAL.md)
defines the separate alert-quality evaluation.

## Measure coding outcomes with the existing agent interface

The existing six-arm comparison covers original-source baseline, deterministic
fast context, the 0.5 and 0.6 contracts, and schema 5 with reuse disabled and
enabled. It accepts a deliberately selected external agent command and keeps
its independent correctness checker outside the agent input.

0.7 adds bounded repair attempts, predetermined sanitized feedback, stopping at
the first independently correct patch, and retained records for interrupted or
failed invocations. All iterations, verification, warm-up, context isolation and
investigation charges remain visible. Unknown provider usage or billing is
`null`. A separate sequence tests task B after task A, related and unrelated
source revisions, and replay under narrower grants.

Prepare the public candidate tasks without running a provider:

```sh
python evaluation/real_coding_corpus.py prepare --pilot --output /tmp/lore-07-pilot
python evaluation/real_coding_corpus.py prepare --output /tmp/lore-07-candidates
python evaluation/adaptive_sequences.py prepare --output /tmp/lore-07-sequences
```

The 30 candidate fault-repair tasks use pinned source from boltons,
more-itertools and python-dotenv. They are public, constructed debugging cases.
They are explicitly not held-out evidence. Correct originals and deliberately
wrong controls exercise their checkers. Independent task/checker authorship,
review captures, a preregistered model and tooling policy, and a captured
execution/egress audit are additional gates for a real study.

See [the real-task preparation guide](../evaluation/REAL_CODING_TASKS.md) and
[the six-arm protocol](../evaluation/ADAPTIVE_TASKS.md) for the actual run and
assessment commands. Paired per-task estimates and 95% bootstrap intervals
describe the collected tasks; a small pilot cannot establish a universal
productivity benefit.

## Make intelligence changes from observed failures

```sh
python evaluation/failure_triage.py triage /absolute/completed-adaptive-run
python evaluation/failure_triage.py validate-change /absolute/completed-adaptive-run /absolute/proposal.json
```

Triage first verifies the retained attempt ledger. A proposed controller change
must cite actual failing samples, exact pilot evidence, the expected corrected
behavior, cost risk and a separate holdout plan. Diagnostic fixtures and an
unverified holdout cannot authorize a claim of measured improvement. The
[failure triage guide](../evaluation/FAILURE_TRIAGE.md) documents those gates.

No new adaptive runtime algorithm is justified merely by an unrun study. The
release scorecard records whether an actual pilot supported such a change.

## Evaluate first contributions and independent learning transfer

```sh
python evaluation/human_onboarding.py prepare --output /tmp/lore-07-human-pilot
```

This prepares a counterbalanced 12-participant study with first-contribution and
distinct transfer tasks. It does not create participants or record consent.
Actual use requires explicit opt-in pseudonymous participant records. Assistance,
hints, mentor interventions, active time, exact submitted patches and independent
checker/reviewer evidence are retained outside Lore's source navigation cache.

The bundled payment/refund and release/withdrawal exercises debug the protocol.
They are not a completed human study. A second task must require adapting a
principle to a different exception; repeating the first solution is not learning
transfer. See [the human protocol](../evaluation/HUMAN_ONBOARDING.md).

The product's existing `lore onboard --task TASK` direct contribution path and
optional tutorial modes remain available. Users do not enter a questionnaire or
lesson unless they choose that experience. No human UX change is attributed to
an observed stumbling point until the corresponding participant evidence exists.

## Compatibility and permission boundaries

The release keeps one retained SQLite knowledge registry, the existing evidence
and decision engine, local CLI entry points, and source-bound disposable caches.
It introduces no background monitoring, automatic project command execution,
new connector, mandatory graphical interface or proprietary coding-agent
dependency. Source reports remain distinct from executed checks and accepted
policy. Host grants remain ceilings for inspection and egress.

External agent and checker processes belong to the evaluation harness and need
an intentionally isolated study environment; they are not a new Lore runtime
capability. Offline tests, reviewed source quotations and checker controls are
reported as their own measurements. Real-model productivity, human transfer and
independently reviewed guardian precision require their corresponding outcome
artifacts before any benefit claim.
