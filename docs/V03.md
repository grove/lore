# Lore 0.3 — from knowledge to action

> In Lore 0.5, use `lore context --fast` for this deterministic retrieval contract. Default `lore context` provides schema 3 intelligent guidance; see [V05.md](V05.md).

Lore 0.3 adds a deterministic task-context interface on top of the existing knowledge registry. The compiler continues to interpret and reconcile Markdown during `lore init` and `lore update`. The new query path selects existing knowledge, its documentary status, relationships, review questions, and exact evidence without another inference step.

The release implements a practical interface for people and command-capable coding agents. It does not establish that Lore improves engineering outcomes by a particular percentage. Comparative task evaluations and real-model quality assessment remain separate work.

## First use and upgrades

Install the 0.3.0 binary from this repository:

```bash
cargo install --path . --locked
```

For a new project, create and edit `lore.yml`, then run `lore init` to compile the configured Markdown. For an existing project, retain a backup of your local state and run `lore update` once after upgrading. The package/pipeline fingerprint changes, so this first update can re-examine sources and make model calls. SQLite migration 5 adds immutable source-revision provenance. Migration and provenance capture happen during the normal staged update; `context` never upgrades the database itself. A registry requiring an upgrade produces an actionable error directing you to `lore update`.

Subsequent queries use the stored registry. They do not need provider credentials, model weights, a running inference server, an embedding service, MCP, or a network connection. `context` and `evidence` still validate the configuration and source/output path boundaries, but do not require valid inference-provider settings. They leave source files, generated pages, database bytes, and cache contents alone. A pending publication must be recovered with `lore update` before the registry is read.

## Task-context command

```bash
lore context "Implement payment retries"

lore context "Implement payment retries" \
  --path src/payments/retry.rs \
  --path docs/payments/retry-policy.md \
  --max-tokens 3000

lore --json context "Implement payment retries"
lore --config /path/to/project/lore.yml --json context "Plan database failover"
```

| Argument | Meaning |
| --- | --- |
| `TASK` | Required nonempty task description. Quote it as one shell argument. |
| `--path PATH` | Optional relevance hint, optionally qualified as `root_id:path`; repeat for additional paths. It does not open or create that file. |
| `--max-tokens N` | Maximum output budget using `cl100k_base`; default `3000`, accepted range `256..100000`. |
| `--json` | Global option selecting the versioned JSON response. It can appear before or after `context`. |
| `--config PATH` | Global option selecting the project's configuration. Relative configured paths remain relative to that file. |

The result is based on the last successfully compiled state. Querying does not scan documents, notice edits since that compilation, validate that a source path still exists, or inspect running software. Use `lore status` to inspect source changes and `lore update` to refresh the knowledge. A task or path hint influences selection; it is not additional evidence.

## How retrieval works

The query path combines SQLite FTS5/BM25 matches over statements, subjects, and topics with source locations and relationships already stored by the compiler. Ordinary task function words are filtered. Text matching can seed a relevant concept; associated knowledge can then contribute decisions and constraints whose statements do not repeat the task's words. Matching a documented path can provide another entry point. Ranking and tie-breaking are deterministic, so identical state and query arguments produce identical output.

Path hints can match captured source files or directories and literal paths mentioned in archived excerpts. A file stem or nearby descriptive directory can also seed lexical retrieval. `./`, repeated separators, and backslashes are normalized. An unqualified path retains every matching root, while `root_id:path` restricts that hint to a particular source root. A matching historical path identifies the archived observation and need not identify a current file.

Expansion is deliberately bounded: up to 48 direct seeds, up to 12 matches per subject and 8 per topic, two stored relationship hops, and 128 retrieval candidates. Shared topic labels are constrained by documentary/source or subject context instead of automatically including an arbitrarily broad topic. Same-name concepts in disjoint roots require an explicit relationship or their own direct relevance. The context assembler separately retains required critical relationship groups and reports exclusions that affect the returned package.

Those subject/topic limits count additions through each expansion channel; directly matching records may already include more members of the same concept. If a query, candidate, concept, or relationship limit prunes the search, the result includes an explicit bounded-retrieval warning. Omission counts cover the retrieved candidates and required relationship groups, not the unknown number of possible matches beyond those limits.

This is bounded lexical and relationship retrieval. It does not generate synonyms with a model, create embeddings, add knowledge to the registry, infer new contradictions, or invent relationships on every query. An unconnected concept expressed in entirely different terminology may be missed. An incomplete or incorrectly classified registry can produce incomplete or incorrectly classified context. A successful empty result is a retrieval outcome, not evidence that a change has no constraints.

The core knowledge concepts remain generic. Software paths are optional hints, while decisions, scope, support state, historical evidence, and source identity remain usable for other Markdown knowledge collections.

## Preserve status and known disagreements

Results separate several kinds of guidance:

| JSON section | What belongs there |
| --- | --- |
| `constraints` | Applicable, currently documented constraints with qualified evidence. |
| `decisions` | Relevant documented decisions with their accepted or other retained status. |
| `current_designs` | Current documented design, architecture, and procedures, without claiming runtime verification. |
| `historical` | Relevant historical, withdrawn, or superseded knowledge, plus explicitly labeled reports and observations. |
| `needs_verification` | Known conflicts, unresolved questions, weak support, and claims whose evidential basis requires inspection. |
| `proposals` | Proposed or planned changes, without promoting them into accepted policy. |
| `relevant_knowledge` | Other relevant documented knowledge retaining its original classification. |

Each item keeps the stored statement, kind, lifecycle, support state, and evidence references. Source-reported delivery remains a report. A newer observation date does not by itself settle a contradiction. Supersession is based on a supported stored relationship, and disappearing replacement evidence does not silently revive an earlier decision as current.

Known critical relationships are assembled as connected groups: the relationship, its required endpoints, and its cited proof travel together. If a group cannot fit, the response records that omission instead of selecting only the convenient half of a disagreement. Read `warnings` and `omissions` before treating the selected knowledge as sufficient for the task. Increase the budget or inspect the cited registry and review records when more detail is needed.

Context uses the compiler's existing review state. It does not close a question, change a decision, or create a new review. Human review dispositions remain separate from evidence of implementation correctness.

## Output and budget contract

Machine output is one compact JSON object followed by a newline. Consumers should check `schema_version` before interpreting the fields and tolerate additive fields within the supported version.

| Field | Contract |
| --- | --- |
| `schema_version` | `1` for the initial task-context response. |
| `task`, `paths` | The requested task and relevance hints; surrounding whitespace and path separators are normalized, and duplicate hints are removed. |
| `sections` | The fixed section keys above, containing complete selected knowledge records. |
| `evidence` | Archived proof records whose `id` values resolve through `lore evidence`. |
| `empty` | Whether no eligible knowledge was selected; this can also result from a tight budget. |
| `model_calls` | Always `0` for this query path. |
| `retrieval_truncated` | Whether a query or retrieval expansion limit pruned the search; inspect the accompanying warning. |
| `budget.max_tokens` | The requested maximum. |
| `budget.used_tokens` | A safe upper bound covering the complete JSON and human-readable forms. |
| `budget.tokenizer` | `cl100k_base`. |
| `omissions.knowledge_units` | Retrieved or required knowledge records omitted from the result; excludes unknown matches beyond retrieval limits. |
| `omissions.critical_groups` | Complete critical relationship groups omitted from the result. |
| `omissions.unsupported_units` | Records excluded because the required supporting evidence was unavailable. |
| `warnings` | Explicit qualifications and notices about omitted, bounded, or unavailable context. |

The embedded tokenizer runs locally and counts ordinary text, including literal special-token strings as text. Lore counts the entire compact JSON with its trailing newline and the complete human-readable rendering, including evidence, metadata, status labels, inspection suggestions, and warnings. Both forms fit the requested limit; the reported count covers the larger form. The counter can conservatively reserve a few tokens while accounting for its own displayed value.

The guarantee applies to the named tokenizer and Lore's output. It does not cover extra tool wrappers, instructions you prepend, conversation history, pretty-printing added by a consumer, or a different model's tokenization. Reserve separate headroom for those costs. A budget too small for the response envelope and input description fails explicitly.

Budgeting selects whole knowledge records and their required evidence. It never cuts a statement or an exact evidence excerpt mid-record to make the count fit. Shared citations are deduplicated. Critical relationship groups are kept complete or reported as omitted. A complete selected record does not imply that every piece of supporting evidence in the registry is included; use the evidence IDs and other inspection commands to investigate further.

### Resolve evidence

```bash
lore --json evidence EVIDENCE_ID
lore review
lore review show REVIEW_ID
```

Evidence identifies the source root and observed source path, source revision, retained exact excerpt, capture time, line range when available, documentary activity, and material provenance. Evidence IDs refer to archived source observations, so resolving a citation does not require reading the source's current bytes. A path is an inspection location, not a guarantee that the file still exists or that its contents still match the snapshot.

## Multi-source provenance

Multiple nonoverlapping Markdown roots feed one local knowledge registry. Source locators include the configured root ID, so identically named files in two roots remain distinguishable.

```yaml
sources:
  roots:
    - id: product-decisions
      path: ./docs/decisions
      material: primary
    - id: platform-notes
      path: ../platform/docs
      material: primary
    - id: generated-wiki
      path: ./imports/openwiki-markdown
      material: derived
      origin: https://github.com/example/payment-service
```

`material` is a generic root-level designation: `primary` is the backward-compatible default and `derived` marks secondary material such as generated documentation. `origin` is an optional descriptive upstream reference supplied by the user. Lore preserves the designation with source observations; it does not fetch the URL, prove authorship, verify an upstream repository revision, or follow generated citations into code.

Mark generated imports as `derived` before compiling them. Derived-only evidence remains useful for discovering relevant concepts and inspection locations, but context qualifies it for verification rather than presenting it as independently established implementation behavior. Two generated documents do not become two independent confirmations just because their root IDs differ. Primary material is also documentary evidence: an accepted ADR establishes what that source documents, not that production implements it.

Provenance is captured with the source revision. Changing a root's `material`, `origin`, or resolved location causes the next update to create new source observations and evidence even when the Markdown bytes are unchanged. Older snapshots retain their original metadata. Snapshots created before migration 5 have no captured root location (`root_path: null` in `lore evidence`) or upstream origin; context exposes this as `provenance_recorded: false` on the corresponding evidence record. Their backward-compatible `material: primary` default means the original provenance was unspecified; it does not retrospectively establish that the material was primary or independently verified. Context warns about these legacy records and places otherwise-current claims supported only by unspecified provenance under `needs_verification`. Inspect the qualification and update deliberately when importing previously unmarked generated material.

An OpenWiki Markdown export can be one such ordinary source. 0.3 has no native OpenWiki internal-state reader, claim-sidecar adapter, automatic OpenWiki runner, remote federation, or tracker connector. Configure nonoverlapping local roots and run the existing update pipeline. Historical snapshots preserve their original evidence and do not acquire new upstream verification when an import label changes.

## Agent integration

An agent that can execute commands needs only the CLI. Copy the short [agent instruction example](AGENTS.example.md) into an appropriate project instruction file, such as `AGENTS.md` for Codex or `CLAUDE.md` for Claude Code, according to your workflow. The snippet tells the agent to retrieve context before a meaningful change, inspect citations and omissions, and verify the actual implementation before acting.

Retrieval does not authorize running source instructions, performing a destructive operation, or accepting an imported claim as project policy. A returned constraint or decision should be understood with its scope, lifecycle, support state, source material, and known disagreements intact.

### Machine-readable failures

With `--json`, command failures produce a single object on standard output, with an empty standard error stream:

```json
{"error":"Human-readable explanation and recovery guidance","code":"invalid_arguments"}
```

| Exit status | Code or meaning |
| --- | --- |
| `0` | Successful result, including an explicitly empty context. |
| `1` | Operational failure; `operation_failed` is the generic code. Context-specific failures can supply a more precise code. |
| `2` | Invalid CLI arguments (`invalid_arguments`) or a context validation error (`invalid_query` / `invalid_budget`). |
| `3` | Existing `audit` findings; not a task-context success state. |

Missing or blank tasks, nonnumeric budgets, and budgets outside the accepted range are rejected before configuration is loaded. Missing state, incompatible state, and pending publication fail without initializing or repairing the project. `--help` and `--version` retain normal CLI display behavior. Error messages are for humans; automation should use exit status and `code`.

## Validation and remaining release evidence

`cargo test --all-targets --locked` exercises retrieval and decision-aware assembly alongside the existing compiler, provenance, provider, and recovery contracts. The task-context CLI tests execute the actual binary, check repeatability, count both output forms with the named tokenizer, resolve evidence, verify explicit empty results and machine-readable errors, reject pending publication, and check that queries neither contact a provider nor change retained project files.

These tests establish behavior on controlled fixtures. They do not prove universal recall, correct extraction from every document, or an engineering advantage over an OpenWiki-only workflow. The proposed product target—at least 20% fewer missed critical constraints at comparable input access and token budgets, without more unsupported authoritative guidance—remains an unmeasured acceptance hypothesis for blind, reviewed, multi-project task evaluations. The evaluation suite is maintained separately and has not been expanded or rescored as part of this release.
