# Lore 0.6: decision-ready project intelligence

**Principle:** conservative about facts, ambitious about understanding, pragmatic
about recommendations.

Lore 0.6 adds a decision contract and optional bounded investigation to the 0.5
intelligence layer. A useful briefing leads with one preferred approach, explains
why it is sensible, states the main trade-off, preserves relevant constraints,
and gives the next implementation action and completion criteria. It can inspect
fresh local source and test declarations to improve that judgment.

## Commands and compatibility

```bash
# Default: schema 4 decision guidance from retained project knowledge.
lore context "Refactor payment retries without changing their behavior"
lore --json context "Refactor payment retries" --max-tokens 6000

# Opt in to a small read-only inspection of the local checkout.
lore context "Refactor payment retries" --inspect --path src/payments

# Investigate consequential uncertainty and revise the action if necessary.
lore --json context "Change payment retries" --investigate --max-tokens 8000

# Override inspection enabled in configuration.
lore context "Refactor payment retries" --no-inspect

# Existing deterministic contract and migration compatibility.
lore --json context "Refactor payment retries" --fast
lore --json context "Refactor payment retries" --schema-version 3

# Disable both guidance and embedding cache reads/writes for this invocation.
lore context "Refactor payment retries" --no-cache
```

Inspection is **opt-in** in 0.6. Its benefit and overhead have not yet been
established on the required independent held-out coding tasks. `--investigate`
implies inspection. `--no-inspect` conflicts with inspection/investigation flags.
`--fast` rejects intelligence-only options and retains its existing schema 2
behavior without inference, checkout discovery, or context-cache changes.

`--schema-version 3` selects the preserved 0.5 implementation. It does not inspect
the checkout; inspection and investigation require schema 4. Configuration
schema versions remain 1 and 2. These are independent of response schemas.

## Decision readiness

| Readiness | Meaning | Contract |
| --- | --- | --- |
| `proceed` | Implementation can begin with the stated boundaries | No hidden required preconditions or material blockers |
| `proceed_after_check` | A small check could change the implementation decision | Exactly one or two specific, inexpensive `required_before_proceeding` checks |
| `blocked` | A significant adopted constraint or policy decision remains unresolved | At least one cited material blocker identifying the decision needed and the proposed deviation |

An ordinary documentation disagreement is not sufficient to block a reversible,
behavior-preserving change. Risk scrutiny and action readiness are separate:
financial or security code can still receive a preserving implementation plan.
An implementation report, incident recollection, or closed issue does not grant
permission to replace an adopted policy.

Checks have three priorities: `required_before_proceeding`,
`recommended_during_implementation`, and `optional_follow_up`. Every check names
an action and explains its decision impact. General instructions such as
"review the implementation and validate behavior" are rejected when they contain
no concrete target or outcome. Suggested tests are recommendations for the
calling developer or agent; Lore never runs them during context generation.

## Schema 4

Successful JSON uses `schema_version: 4` and `mode: intelligent`:

| Field | Contents |
| --- | --- |
| `brief.readiness`, `brief.change_kind` | Action readiness and preserving/changing/policy-changing classification |
| `brief.preferred_approach` | One preferred implementation action |
| `brief.rationale`, `brief.main_tradeoff` | Evidence-linked reasoning and the main cost or compromise |
| `brief.next_action`, `brief.completion_criteria` | The next concrete step and observable completion conditions |
| `brief.facts` | Exact copied registry statements, lifecycle, scope, qualifications, and documentary/imported provenance |
| `brief.hypotheses` | Explicit hypotheses with applicability, confidence, alternatives, and supporting references |
| `brief.heuristics` | General engineering principles, separately tagged and without invented project citations |
| `brief.constraints`, `brief.material_blockers` | Treatment of every selected adopted constraint and any actual policy decision required |
| `brief.checks`, `brief.risks` | Prioritized checks and likely mistakes or regressions |
| `brief.implementation_seams` | Confirmed inspected paths and the observation IDs that justify them |
| `brief.counterevidence`, `brief.remaining_uncertainty` | Evidence against earlier hypotheses and what still matters |
| `evidence` | Exact retained evidence/revision manifests, resolved through `lore evidence ID` |
| `inspection` | Checkout identity, bounded file index, complete local observations, I/O budgets, and diagnostics |
| `investigation` | Selected hypotheses/checks, prior and revised recommendations, stopping reason, and inference budgets |
| `checkout_egress` | Permission and whether this invocation actually passed checkout-derived content to a model |
| `revision_key`, `cache_status`, `model_calls` | Revision binding, cache outcome, and actual inference attempts |
| `budget`, `omissions`, `brief_items_omitted` | Complete-output token accounting and explicit omissions |

Advice refers separately to `evidence_ids` and `observation_ids`. A local
observation is self-contained:

```json
{
  "id": "co_<sha256-of-observation-tuple>",
  "path": "src/payments/retry.rs",
  "start_line": 10,
  "end_line": 11,
  "excerpt": "const MAX_ATTEMPTS: usize = 5;\n// Preserve the idempotency key.\n",
  "content_hash": "sha256:<hash-of-complete-file-bytes>",
  "kind": "static_source",
  "qualification": "Static source inspection; not proof of runtime behavior or test execution."
}
```

This example illustrates the shape, not a real project observation. Paths are
checkout-relative, line ranges are one-based and inclusive, and excerpts retain
their original bytes and line endings. The content hash covers the complete
file, not only the excerpt. The observation ID hashes the compact JSON tuple
`[path, start_line, end_line, excerpt, content_hash]` with SHA-256. Actual
qualifications explicitly distinguish static source/test inspection from runtime
or deployment verification. Local IDs resolve in the response, not the accepted
registry. They are never sent to `lore evidence` as documentary IDs.

Every generated decision passes structural/evidence/readiness validation and a
separate model support check. That check can reject unsupported project claims,
incorrect authority, unnecessary blocking, or failure to revise after material
counterevidence. It is a fallible model review, not independent execution proof.

## Inspection and privacy

```yaml
context:
  cache: true
  inspection:
    enabled: false
    # Optional for exported source trees without .git; relative to lore.yml.
    root: .
    max_files: 6
    max_file_bytes: 65536
    max_total_bytes: 262144
    max_index_entries: 2000
    max_elapsed_ms: 1000
    max_excerpt_lines: 80
  investigation:
    max_rounds: 2
    max_model_calls: 6
    timeout_seconds: 30
privacy:
  local_only: true
  allow_checkout_egress: false
```

Without an explicit root, discovery uses a safely discoverable `.git` ancestor
of the configuration directory. It does not follow worktree `.git` target files
or scan arbitrary source roots. Candidate selection combines task terms,
recorded locations, supplied path hints, and related test filenames. The initial
inspection reads at most three relevant files, leaving capacity for follow-up.

The inspector refuses traversal, symlinks and reparse points, hidden credential
locations, likely secret content, binary files, generated files, configured
exclusions, ignored files, and Lore output/state directories. Discovery itself
has an entry limit and time budget. `.gitignore` reads count toward the byte
budget. Unix opens use descriptor-relative no-follow operations; Windows uses
guarded handles that reject reparse points and prevent directory replacement.
Files that cannot be opened safely remain unavailable.

**Existing hosted documentary permission does not authorize checkout egress.**
For a hosted model, fresh code, derived observations, and discovered candidate
filenames are withheld unless `privacy.allow_checkout_egress: true` or
`--allow-checkout-egress` explicitly permits them. `privacy.local_only: true`
still forbids a hosted provider. Only a local, non-cloud-tagged Ollama model receives implicit local checkout
permission. OpenAI-compatible providers require separate checkout permission
even at a loopback endpoint, because that endpoint can be a forwarding proxy.
A local Ollama cloud-tagged model is also treated as hosted for this gate. Embeddings process retained knowledge and
the supplied task/path hints; checkout observations are never embedded.

Without checkout egress permission, Lore can return local observations to the
caller alongside retained-knowledge guidance. Its metadata states that the model
did not use those observations, and deeper model-driven inspection is skipped.
No context mode executes code, launches a shell, runs tests, changes source
files, updates an issue tracker, or writes accepted knowledge.

## Bounded investigation

The model may select one exact `file_<hash>` ID from the current candidate
allowlist. It cannot supply a filesystem path or command as a capability.
Each round identifies the consequential uncertainty, records a hypothesis and
the expected distinguishing evidence, reads the selected file, and asks for a
revised decision. The final support check sees the previous and revised actions.
Material counterevidence must change the preferred implementation action;
retelling the same unsupported recommendation is rejected.

| Resource | Default | Hard ceiling |
| --- | --- | --- |
| Distinct inspected source files | 6 | 20 |
| Bytes in one source file | 65,536 | 262,144 |
| Total read bytes, including rereads and ignore rules | 262,144 | 1,048,576 |
| Discovered directory entries | 2,000 | 20,000 |
| Cumulative inspection I/O time | 1 second | 10 seconds |
| Lines in one excerpt | 80, reduced for small output budgets | 200 |
| Investigation rounds | 2 | 2 |
| Inference attempts for a schema 4 query | 6 | 8 |
| Schema 4 query deadline, including retrieval | 30 seconds | 60 seconds |

The normal decision path uses synthesis and a support check. Optional semantic
retrieval reserves room for both and permits at most two embedding calls in one
query. Investigation reserves a final support check before starting each round;
retrieval calls can therefore reduce the number of available rounds. Transport
retries are disabled for schema 4 to keep attempted calls within the allowance.
Failed, invalid, and timed-out model attempts consume budget. Time spent waiting
for inference does not consume the separate inspection I/O allowance.

## Revision caching and fallback

Schema 4 caches live under `.lore/context-cache/decision-*.json`, separate from
`state.db` and the schema 3 cache. Identity includes task, source selection and
revisions, model and endpoint, reasoning settings, configuration, privacy,
query options, prompt/schema versions, checkout identity, and the relevant
allowlisted file index. A cache hit rehashes **every inspected file**, including
files selected only in a deeper round. Additions, removals, ignore changes,
same-size edits, changed permissions/options, and revised documentary evidence
invalidate affected guidance. An incomplete file index cannot authorize reuse.

All consumed local observations are revalidated after reasoning as well. If
they change or revalidation cannot fit the read budget, generated advice is
discarded. The query does not spend an unbounded new budget to retry. A stale
cache probe consumes the same read allowance as other inspections.

Inference, inspection, and cache failures are explicit. `mode: fast_fallback`
may contain `brief.generation_basis: deterministic_fallback` with copied evidence
and a provisional scope check. It does not claim fresh model assessment. If the
whole decision cannot fit, the response retains the deterministic retrieval
fields with schema 4, `fallback_reason`, cache status, inspection/investigation
status, and egress metadata. Required constraints and hash-bound references are
never silently detached to fit a budget. A path/task too large for even fallback
metadata returns the existing structured `invalid_budget` error.

## Evaluation and release status

[The 0.6 evaluation guide](../evaluation/DECISION_INTELLIGENCE.md) compares original
sources, fast context, 0.5 context, and 0.6 context with the same coding task,
source snapshot, model/settings, and verification program. It records material
decision mistakes, constraint preservation, unnecessary blocking, hypothesis
revision, implementation quality, measured latency, and known costs.

Release-quality claims require at least three independent held-out projects and
independent human review. The target is a **15% relative reduction in material
decision mistakes versus 0.5** when that baseline has nonzero mistakes. This is
a target, not an established result. Synthetic fixtures test contracts and do
not satisfy the empirical gate. Time to correct completion requires an observed
completion/correction process; a single initial response does not establish it.
Egress and source-preservation assertions require actual audit evidence.

Until those measurements justify the additional overhead, inspection remains
opt-in. Lore 0.6 introduces no graph database, mandatory MCP service, coding-agent
framework, background agents, GUI, or autonomous changes. OpenWiki, Engram, and
Beads keep their existing roles; Lore uses their retained evidence to help the
caller make the next engineering decision.
